# Extreme cases of the HPC controller

What the controller (`internal/`), the follower and the Python runner (`runner/`) do under pressure, and the
automated test that proves it. Source of intent: PRD #1461 (section 10 threats T-xx, decisions D-xx).
The lessons the old in-pod waiter learned in live runs are mapped to tests in [live-lessons.md](live-lessons.md).

Status legend

| Status | Meaning |
|---|---|
| COVERED | proven by a test that existed before this document |
| ADDED | a test added with this document (alone or on top of existing proof) |
| FIXED | the new test found a bug; the fix is in the same change |
| OPEN | real gap found by reading the code; not fixed here, needs an owner decision (see "Open findings") |
| LIVE ONLY | cannot be proven with the fakes; the reason is given |

Test references are `file::name`. Go specs that are Ginkgo `It`s are cited by their text. `internal/controller`
specs run against envtest; the site is played by status writes (what the runner and the site poller would write).

## Findings

| ID | Severity | State |
|---|---|---|
| F-1 | Medium | FIXED: runner Job failed (deadline, 5 failed pods) or gone while the site job lives: orphan sweep, 2.13 |
| F-2 | Low | OPEN: a purged site job is polled until the deadline; the message does not say the site lost it. Now partly answered by the sweep (`SITE_UNKNOWN` after 10 min) but only once the runner Job is gone |
| F-3 | Medium | FIXED: a cancel is no longer finalised without the site's proof or the documented decision rule (2.12, 2.13, 2.14) |
| F-4 | Low | OPEN: after `LOST_HOST_RESUBMITS` the runner keeps watching a job held by a dead host until the deadline, with no explicit reason |
| F-5 | Medium | FIXED: HPCSite/project binding lost under a running job (9.1, 9.2), with a grace period |
| F-6 | Low | OPEN: a dead login node with a healthy Slurm API delays the submit by up to the 4 h staging budget (2.10). By design, but long |
| F-7 | Low | FIXED: `slots.py` TERM race (3.9) |

Known limits of the fixes: a job whose runner died between the site accepting the submit and the first state report has no recorded site job id and is not swept (that window is a few seconds; the next pod of a live runner Job adopts by key). A job whose HPCSite is gone for good cannot get a cancel-only runner (it needs the site's endpoint and identity): after the grace its runner Job is deleted (SIGTERM cancels), and if that is not proven only the give-up time ends the sweep. A run reported terminal while the HPCSite is missing is settled only after the site is back or the grace has passed, and then as `Cancelled`.
